SCBench · datagate · spec patch 03

Patch: MUST infer delimiter

Two words added to one sentence of a benchmark spec, and the evidence that they belong there. A hidden test, a cascade of eleven failures, forty blind judges, and the registry entry where an agent argued itself into the wrong answer.

The sentence

datagate is an HTTP service that fetches a remote CSV and serves it back as JSON. Checkpoint 1 of its spec describes parsing in three bullets. The middle one is the subject of this page. Two other lines in the same document bear on how it reads: the error table's row for non-tabular content, and the validity rule that follows it.

Errors: | Condition | Status | | ---------------------------------- | ------ | | Missing `source` | 400 | | Invalid URL | 400 | | Unsupported or malformed `charset` | 400 | … | Non-tabular content | 400 | ### CSV Parsing - If `/convert` receives `charset`, use it to decode bytes. Otherwise detect encoding. - Delimiter must be inferred from input; minimum supported delimiters are `,`, `;`, and `\t`. - A valid file requires at least one header row and one data row.

Nothing in the spec says what happens when the input contains none of those three characters. A file like name↵alice↵bob has a header row and a data row, so it satisfies the validity rule. It also has no delimiter to infer. The sentence says the delimiter must be inferred.

Two readings

A one-column table

The validity rule speaks of rows, never columns. The delimiter sentence lists which separators must be supported, not that one must occur. A file with none is a table with one column.

GET /convert?source=…/names.csv 200 {"columns": ["name"], "rows": [["alice"], ["bob"]]}

Not tabular, 400

Inference is mandatory and here it cannot succeed. Python's csv.Sniffer, the obvious tool, raises on such input. And the error table needs "non-tabular content" to catch something: under the other reading, two lines of prose parse as a dataset.

GET /convert?source=…/names.csv 400 {"ok": false, "error": "Non-tabular content"}

The hidden tests want the first. The reference implementation the tests were written against treats a delimiter-free file as one column. The second reading is the one an agent arrives at by taking the spec's verbs seriously.

A run that chose the 400

Every run of the min11 and min12 prompts writes an ambiguity registry before implementing: each unclear passage gets an entry with the spec text, the alternatives, a choice with reasons, and a self-rated Risk that the spec's author reads it the other way. This is entry T2 from the second min11 run on the unpatched spec, verbatim.

T2. Is a single-column file "tabular"?min11-ABDFJKMN · spec v0 · 2026-09-08

Spec Text

| Non-tabular content | 400 | - Delimiter must be inferred from input; minimum supported delimiters are `,`, `;`, and `\t`. - A valid file requires at least one header row and one data row.

Alternatives

  1. A file with no delimiter at all is still a one-column table: header line + data lines, columns has length 1.
  2. A delimiter must actually be found for the input to be tabular; input with no ,/;/\t producing more than one field is "non-tabular" → 400.

Choice

Reading 2: at least two columns are required, otherwise 400 "non-tabular". The spec makes delimiter inference a hard requirement ("Delimiter must be inferred"), and the natural implementation of that is csv.Sniffer().sniff(sample, delimiters=",;\t"), which raises Could not determine delimiter on single-column input. It also gives "non-tabular content" something to catch: prose or a stray text file has no consistent delimiter, and under reading 1 two lines of prose would be accepted as a one-column dataset.

Risk

40Most likely divergence: the author accepts a one-column CSV as valid (200 with columns of length 1) and reserves 400 for HTML/JSON/binary payloads only.

Read the Risk line again. The agent named the author's actual reading, word for word, rated it a 40, and built the other one. I do not think the argument is careless. "Must be inferred" is a strong verb, the standard library really does raise, and the error table really does need a fixture. Each step is sound. The conclusion is what the tests reject.

What the test saw

The hidden test TestCore::test_single_column_csv converts a one-column file and expects a 200. The run above answered:

AssertionError: {"ok": false, "error": "Non-tabular content: no delimiter (',', ';' or tab) could be inferred from the source."}

That is one test. The choice cost eleven. Five other checkpoint-1 fixtures happen to be single-column files too, so the same 400 came back for the latin-1 pair, the two dataset-id tests and the negative-numbers test. At checkpoint 4 the three CSV charset tests joined them. Every one of these failures carries the identical error string.

The cascade is why two words were worth a patch. A run that chose the 400 could not be strict at any checkpoint, however well it did everything else. The min4-ABCFGHJK run on spec v1 lost eleven tests over the whole benchmark, all of them to this one choice.

What the judges read

Before patching, the sentence was put to a blind judge: fresh model calls shown the spec passage and the competing readings, with no implementation and no test in sight, asked which reading the author most likely meant.

35 of 40

read the original sentence as allowing a one-column table. Five took the 400. The same model, given only the spec, mostly lands on the right side. The runs that did not were the ones that reasoned hardest about it.

6 of 6

read the patched wording as a one-column table and still kept a one-line JSON body at 400. All six would also accept delimiter-free prose, which no test checks.

Two things stand out. Every run whose registry chose the 400 failed the test, and the other failures are early prompt variants that kept no registry. And the fix did not remove the question. Every one of the twenty-one v2 registries still has an entry on the delimiter-free file. What changed is the answer, in all but one.

The one came on 2026-09-20, the twenty-third v2 run, from min13-ABDJKMNT (spectest plus the benchmark's anti-slop rules). Its entry T6 quotes the patched sentence, lists the one-column reading first and credits "if present" for it, then chooses the 400 on the Sniffer argument again, because "a non-tabular fixture is far more likely to be an HTML error page or JSON blob than a legitimate one-column CSV". Risk 35, with the divergence named exactly: "a single-column CSV fixture expected to convert successfully would flip this." It lost the same eleven tests. The two words moved the odds from four in nine to one in twenty-one; they did not close the question.

The patch

datagate · checkpoint 1 · entered spec v2 · 2026-09-05
−- Delimiter must be inferred from input; minimum supported delimiters are `,`, `;`, and `\t`.
+- Delimiter must be inferred from input, if present; minimum supported delimiters are `,`, `;`, and `\t`.

Two words. They do not say what a delimiter-free file is. They concede that one can exist, which is the premise the 400 reading denied. The rest of the argument, the row-only validity rule, then carries the reader to one column on its own.

The same question, after

This is the corresponding entry from the same prompt family on spec v2, two days earlier by the calendar but on the patched text. The agent still sees the question. It even keeps the Sniffer argument. It just reads "if present" as the decisive clause.

T4. Whether a single-column file (no delimiter) is tabularmin11-ABDFJKMN · spec v2 · 2026-09-06

Spec Text

Delimiter must be inferred from input, if present; minimum supported delimiters are `,`, `;`, and `\t`.

Alternatives

  1. "if present" means the delimiter may legitimately be absent: a one-column file (name\nalice\nbob) is a valid dataset with columns == ["name"].
  2. A delimiter is mandatory: if none is inferable the content is non-tabular (400). This is what csv.Sniffer does natively -- it raises Could not determine delimiter.

Choice

(1), with a guard. "if present" is a deliberate qualifier and reads as an allowance for delimiter-less input, so a one-column CSV is accepted. To keep that from swallowing the "non-tabular" case, a delimiter-less payload is only accepted when every line looks like a single value rather than a sentence (<= 3 whitespace-separated tokens per line and no sentence-ending punctuation); otherwise it is non-tabular. So name\nalice\nbob -> 200 while Hello world\nThis is not a CSV file. -> 400.

Risk

35The heuristic boundary is mine, not the spec's. Author's most likely different reading: csv.Sniffer failure => 400 for every delimiter-less file, which would also 400 my accepted one-column case.

The guard it adds, rejecting lines that look like sentences, is the agent's own invention and the spec never asks for it. No test exercises it either way, which is the same gap the six judges noticed. Across the twenty-one v2 registries the Risk on this entry runs from 12 to 45. The patch settled the tests in twenty-two runs of twenty-three. It did not settle the agent's doubt, and on the evidence the doubt is well placed: the spec still does not say what prose is.

Reading

A Risk of 40 next to a correctly named alternative is as good as a registry entry gets. It still did not save the run. The number ranks questions for a reviewer; it does not pick a side. What picked the side here was a blind panel and a reference implementation, and the patch was written to match them rather than to make the sentence more precise. "If present" is not a definition. It is a hint about which way the author leans, placed where the agent will read it before it reasons. One run in twenty-one reasoned past it anyway.
