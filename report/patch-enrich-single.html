SCBench · datagate · spec patch 02

Patch: only exact enrich=yes

One word added to one sentence of a benchmark spec, and what it did to the reading. A hidden test the reasoning prompts kept failing, the registry entries that argued for the first value, and twenty-two runs on the patched text without a miss.

The sentence

datagate is an HTTP service that fetches a remote CSV and serves it back as JSON. Checkpoint 7 of its spec adds optional enrichment: pass enrich=yes on /convert and the dataset gains a summary and per-column details. The trigger is two sentences long.

### Enrichment trigger Only exact `enrich=yes` enables enrichment. All other states keep enrichment off. Success response remains: {"ok": true, "endpoint": "/datasets/<id>"}

A query string can carry the same parameter twice. ?enrich=yes&enrich=no is a legal request, and the sentence says nothing about it. "Exact" is about the spelling of a value. Whether two values count as a state, and which state, is left to the reader.

Two readings

The first value decides

The sentence is an equality test on a value. Web frameworks hand back the first value of a repeated parameter, so enrich=yes&enrich=no is enrich=yes and enrichment is on. The spec spells out a 400 for a repeated force and says nothing of the kind here, so a repeat is not an error either.

GET /convert?source=…&enrich=yes&enrich=no GET /datasets/<id> 200 {…, "dataset_summary": {…}, "column_details": {…}}

A repeat is another state

"All other states keep enrichment off" is the operative clause. The request as sent is not enrich=yes alone, so it is one of the other states: the request succeeds and nothing is enriched, whatever order the values came in.

GET /convert?source=…&enrich=yes&enrich=no GET /datasets/<id> 200 {"columns": […], "rows": […], "total": 1}

The hidden tests want the second. The reference implementation reads the whole list of values and enriches only when the list is exactly ["yes"]. The first reading is the one an agent reaches by asking what the framework does.

Ambiguity analysis

A run that chose the first value

Every run of the spectest prompts writes an ambiguity registry before implementing: each unclear passage gets an entry with the spec text, the alternatives, a choice with reasons, and a self-rated Risk that the spec's author reads it the other way. This is entry T89 from the first min12 run on the unpatched spec, verbatim.

T89. What "only exact enrich=yes" does with a repeated enrich parametermin12-ABDJKMN · spec v0 · 2026-09-09

Spec Text

Only exact `enrich=yes` enables enrichment. All other states keep enrichment off.

Alternatives

  1. The first value decides: ?enrich=yes&enrich=no enables enrichment, the way request.args.get("enrich") == "yes" behaves.
  2. Repetition is one of the "other states": enrichment is on only when there is exactly one enrich value and it is yes.
  3. A repeated enrich is HTTP 400, by analogy with force.

Choice

Alternative 1. The section is written entirely in terms of the parameter's value, and the trigger sentence has the shape of a single equality test; the spec pointedly does not repeat the "any additional value is HTTP 400" rule it states explicitly for force, so 3 would be inventing an error. Given no such rule, the ordinary query-string reading takes the first value.

Risk

15Most likely author reading if different: alternative 2 — repetition treated as "some other state" and therefore off.

The Risk line names the author's reading and rates it 15. The argument above it is careful: the section does speak only of values, the spec does give force a repeat rule and withholds one here, and the framework really does return the first value. What decided it in the end is the last sentence, "the ordinary query-string reading takes the first value". The library's default became the spec's meaning.

What the test saw

The hidden test test_duplicate_enrich_params_do_not_enable_metadata sends enrich twice, once as yes and once as no, in both orders, then reads the dataset back and expects neither dataset_summary nor column_details. The run above answered the yes-then-no case:

AssertionError: assert 'dataset_summary' not in {'column_details': {'name': {…}, 'val': {…}}, 'columns': ['name', 'val'], 'dataset_summary': {'column_count': 2, 'filetype': 'csv', 'row_count': 1}, 'ok': True, …}

The no-then-yes case passes under either reading, since the first value there is no. So this choice costs exactly one test at the last checkpoint and nothing downstream: there is no cascade here, which is the opposite of the delimiter sentence. What makes it worth a page is who lost it.

The prompts that reason about a sentence are the ones a sentence can lead astray, and on the original text seven registries in nine went to the first value, at Risks between 12 and 25.

The patch

datagate · checkpoint 7 · entered spec v2 · 2026-09-05
−Only exact `enrich=yes` enables enrichment.
+Only a single, exact `enrich=yes` enables enrichment.

One word, and an article to carry it. "Exact" already governs the spelling, so "single" can only be about how many times the parameter appears. It does not say what a second enrich does. It says a second one is not the trigger, which is all the test asks.

The same question, after

This is the corresponding entry from the same prompt on spec v2. The agent still sees the question and still names the framework's one-liner as what the author probably wrote. It reads "single" as a count and passes.

T79 — enrich supplied more than once, including enrich=yes&enrich=yesmin12-ABDJKMN · spec v2 · 2026-09-14

Spec Text

Only a single, exact `enrich=yes` enables enrichment.

Alternatives

  1. "Single" counts occurrences: two enrich parameters keep enrichment off even when both read yes.
  2. "Single" only stresses the exact spelling; a repeated parameter is resolved the way the web framework resolves it (first or last wins), so enrich=yes&enrich=yes enriches.
  3. Repetition is a 400, as it is for force (T61).

Choice

Alternative 1. The word "single" is doing work next to "exact" — exact already covers the spelling of the value, so "single" must be about how many times the parameter appears. Combined with "all other states keep enrichment off" (T78), the natural implementation reads the whole list of values and enriches only when it is exactly ["yes"].

Risk

40Author most likely prefers: enrich=yes&enrich=yes (and enrich=no&enrich=yes) enriching, because a one-line request.args.get("enrich") == "yes" sees only the first value and is the shortest way to implement "exact enrich=yes".

The Risk went up, from 15 for the wrong answer to 40 for the right one. That is the honest direction. The patched sentence names a state without defining what it does, and the agent can see that a one-line implementation would disagree with it. Across the twenty v2 registries the Risk on this entry runs from 5 to 40, and none of them took the first value.

The original text could be read right

Two of the nine v0 registries chose off from the unpatched sentence. This is the second min11 run's entry, which lists first-value-wins as its third alternative and rejects it.

T102. What exactly counts as enrich=yesmin11-ABDFJKMN · spec v0 · 2026-09-08

Spec Text

`/convert` supports optional ingestion enrichment with `enrich=yes`. Only exact `enrich=yes` enables enrichment. All other states keep enrichment off.

Alternatives

  1. Enrichment is on only when enrich appears exactly once with the exact value yes; every other state — absent, ?enrich, enrich=, enrich=YES, enrich=Yes, enrich=1, enrich=true, enrich=yes%20, and any repeat such as enrich=yes&enrich=yes — leaves enrichment off, and none of them is an error.
  2. Same, but a repeated enrich is HTTP 400, by analogy with force.
  3. The first value wins, so enrich=yes&enrich=no enriches.

Choice

Reading 1. "Only exact" rules out case folding and truthy synonyms, and "All other states keep enrichment off" names the consequence of every other state — it says the request still succeeds with enrichment off, not that it fails, so reading 2 is excluded. A repeat is one of those "other states": the parameter as sent is not enrich=yes alone, so it does not clear the "only exact" bar, which also excludes reading 3. Unlike force, enrich is given no "may appear at most once" rule anywhere in the spec.

Risk

25Most likely divergence: the author tests params.get("enrich") == "yes" on a single-value parse (or "yes" in values), so enrich=yes&enrich=yes enriches instead of staying off.

The route is "all other states". Where T89 read the trigger sentence as an equality test and asked what the framework returns, T102 read the second sentence as the rule and asked whether a repeated parameter is enrich=yes alone. It is not, so it is another state, so it is off. The patch does not add that argument; it makes it the only one left.

Reading

A one-word patch moved the reasoning prompts from seven wrong in nine to none in twenty, on a sentence the bare prompt was already getting right. The word works by attaching to "exact", which every registry had already fastened on, and pointing it at count instead of spelling. Nothing about the state itself became clearer, and the agents' Risk numbers say so. That is what a good patch to a spec looks like from the inside: not a definition, a word placed where the reader is already looking, before the reasoning starts.
