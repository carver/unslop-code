SlopCodeBench · Phase 0 control

Sonnet 4.6 on Claude Code 2.1.44, reproduced on a Max subscription

Six dev problems, 33 checkpoints, unmodified benchmark, no API-key spend. Compared against the leaderboard's 36-problem row and the paper's Table 1.

Verdict

Reproduced well enough to proceed. Cost per checkpoint lands within 10% of the leaderboard and the extrapolated net cost within 5% of the paper; solve-rate gaps sit inside what 33 checkpoints can resolve. Two fixes first: lift the turn cap, then measure run-to-run noise.

The 5-generation models triple the isolated solve rate (9.1% to 24.2% Opus, 27.3% Fable) and improve every quality score; the strict/iso gap stays wide open on all three, and each model's losses trace to a few early misreadings carried forward as regressions. Fable uses the fewest tokens and steps of the three (its token count priced at Sonnet rates is $1.45/ckpt, below Sonnet's own $1.60) - its $5.31/ckpt is purely the $10/$50 list price. Budget notes: the weekly rate-limit window weights models (~3x per token for Fable: ~22 points for this run vs ~8-9 for the others), so full-holdout seeds fit on Opus (~55 points) but not comfortably on Fable (~130); Fable also fills a 5-hour window in about 4 hours of work, handled here by pausing at problem boundaries and auto-resuming after resets. The Sonnet column is the capped 2.1.44 control, so cross-model deltas carry that confound. Details in notes/dev6-opus5.md and notes/dev6-fable5.md.

Smoke run

file_backup, four checkpoints, before the subset

The first end-to-end run on the subscription path: strict 0/4, isolated 0/4, core 4/4, $3.06 total ($0.77 per checkpoint), 22 minutes. The agent passed the single core test every time but never all functionality tests (23/27, 9/17, 11/17, 16/20) and regressions crept in from checkpoint 2 on (28/32, 38/50, 50/68). Thinking blocks appeared in every checkpoint; no errors, empty stderr.

file_backup is a holdout problem that the plan named for the smoke run before the split existed. Its run outputs (transcripts, snapshots, per-test results) were deleted on 2026-08-30 so nothing from a holdout problem sits on disk; the summary above is the surviving record.

Surprises

Things that looked wrong or need remembering

  1. The turn cap bound on 4 of 33 checkpoints. rejector 5 and sith 1, 3, 4 ended with error_max_turns at 101 turns. The repo default step_limit: 100 becomes --max-turns 100, but the paper's setup says "no turn or cost cap" with a two-hour wall clock. Each capped checkpoint had already cost $4 to $6.50 and 20 to 34 minutes; the snapshot at the cap was still evaluated and three of the four count as core-solved. Fixed in the agent config after this run.
  2. The agent killed its own harness once. On datagate checkpoint 1 it ran pkill -f "datagate.py start". The harness passes the whole prompt as an argument to the claude process, so the pattern matched Claude Code itself: tool result "Exit code 144", transcript ends with no result payload. The runner evaluated the snapshot anyway (48/50, core solved, $0.14). The leaderboard's harness has the same hazard.
  3. uvx was missing on the host. The static-metrics step shells out to uvx scb-check==0.1.3; this box had uv without the uvx binary, so the first report silently lacked erosion and verbosity. A two-line shim fixed it, and bin/scbcheck writes per-checkpoint reports because metrics static keeps them only in the aggregate.
  4. Haiku sub-agents and 1-hour cache are Claude Code's own choices. 26 of 37 checkpoints across both runs include claude-haiku-4-5 messages from Task sub-agents, and most checkpoints wrote to the 1-hour prompt cache. Both are part of the leaderboard's cost too and explain why Claude Code's reported cost runs about 10% above a Sonnet-only recomputation.
  5. Nothing else went wrong. No rate-limit hits, retries, timeouts, Docker failures or eval failures: zero error-level lines in run_agent.log and empty stderr on every checkpoint.

Recommendation

Proceed, after two fixes

What matched: cost per checkpoint ($1.78 vs $1.96), extrapolated net cost ($367 vs $383.83), erosion (0.80 vs 0.74), cloned % (0.088 vs 0.093), the shape of the results (core solves common, strict rare, regressions accumulating from checkpoint 2 on), and model, version, thinking and prompt confirmed from every transcript. Subscription auth worked with zero API-key exposure. Solve rates are lower than the board (isolated 9.1% vs 16.8%, core 48.5% vs 56.1%) but inside what 33 checkpoints can resolve.

1. Lift the turn cap (done)

Agent config now uses step_limit: 0 (no --max-turns), timeout: 7200 to mirror the paper's two-hour limit, and a per-problem net_cost_limit: 60 as the rate-limit guard. Twelve percent of checkpoints hit the old cap, all Hard, which is where a skills intervention would most plausibly move isolated and core solves. The run above is therefore a capped reference, not seed 1 of a noise estimate.

2. Measure noise before any treatment

With strict at 2/33 and isolated at 3/33, a skills effect on those columns is not measurable on the dev set; core (16/33) and the quality scores are the dev-set signals. Two more dev6 control runs under the new config (about $59, 6 h and 8 weekly points each) give a variance estimate. The holdout (30 problems, 163 checkpoints) is where strict and isolated can be judged, at about $310 and 31 h per seed.

Still to decide: whether the primary outcome for the skills experiment is core solve plus erosion and verbosity rather than strict solve.
